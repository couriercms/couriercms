# ADR-0009: Invite-only authentication and workspace authorization

- Status: Accepted
- Date: 2026-09-24

## Context

CourierCMS is initially self-hosted and normally operated by a small team, but its
authorization boundary must not assume a permanently single-user installation.
The product may later be offered as a hosted service. Authentication, customer
ownership, and a future CourierCMS platform operator are different concerns.

## Decision

CourierCMS uses passwordless, email magic-link authentication. There is no public
registration. An owner or administrator invites each user into a Workspace.

Every domain record belongs to a Workspace, even though V0 exposes one default
Workspace and no workspace switcher. Authorization is based on the active
Workspace Membership carried in the request scope:

- `owner`: full workspace control, including assigning owners and administrators
- `admin`: manages CourierCMS configuration and operator/viewer access
- `operator`: runs Routes and retries failed work
- `viewer`: read-only operational visibility

At least one active owner must always remain. A user cannot block their own
membership. Users are blocked rather than deleted, preserving Run attribution
and audit history. Blocking revokes all active sessions.

The bootstrap command may create only the first owner. After that, membership
changes happen through the authenticated Users page.

A future hosted-service platform administrator is not a Workspace owner. Any
platform-level support or billing role requires a separate model, explicit
impersonation controls, and its own audit trail.

## Consequences

- Application context functions accept a caller Scope and constrain queries by
  Workspace.
- Authentication alone is insufficient; active membership is required.
- Production deployments require working outbound email before users can sign in.
- V0 keeps a single-Workspace UI while retaining a safe tenant boundary in data.
- Password fields generated by the authentication foundation are not exposed as
  a login mechanism and may be removed in a later schema cleanup.

## Alternatives considered

- Public registration was rejected because CourierCMS administers sensitive CMS
  credentials and is intended for a small, controlled operator group.
- One global `is_admin` flag was rejected because it mixes customer ownership
  with future hosted-platform administration.
- A special undeletable user row was rejected in favor of the invariant that at
  least one active owner membership must remain.
